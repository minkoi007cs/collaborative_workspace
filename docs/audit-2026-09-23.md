# SyncSpace audit — 2026-09-23

Scope: the local repository and the empty `minkoi007cs/collaborative_workspace` GitHub repository. The local project had no commits at audit start. This review covers implemented code; roadmap features are evaluated as gaps, not bugs in working features.

## Findings

| Priority | Finding | Evidence and impact | Resolution |
| --- | --- | --- | --- |
| High | No product authentication or protected user route existed after Phase 1. | Only `/api/v1/health` and a static landing page existed; users could not use the application. | Added Supabase SSR email/password and Google OAuth flows, verified API bearer tokens, local profile API, and protected `/app`. Live provider flow awaits project credentials. |
| High | Initial Phase 2 draft did not boot the API. | `AuthGuard` depended on `AuthService`, which was not exported from `AuthModule`; Nest exited during dependency injection. | Exported the service and retained an API integration test that boots the full module tree. |
| High | Authentication must not trust browser cookies or caller supplied user IDs. | A forged cookie or user ID could impersonate another user if used directly. | Next.js calls `getClaims()` before using a session; Nest validates signature, issuer, audience, expiration, role, and non-anonymous subject via project JWKS. `/users/me` derives identity only from verified bearer token. |
| Medium | Supabase cookie refresh responses need private cache headers. | A shared cache could serve a response containing another user's refreshed cookies. | Middleware forwards Supabase cache headers with refreshed cookies; protected page uses dynamic rendering and no-store API fetches. |
| Medium | Auth setup details leaked into the product UI. | The initial sign-up page told end users to add project environment variables. | Replaced with a short availability message; setup remains in README. |
| Medium | Phase 1 UI had no navigation to an account flow. | The page was a portfolio-like static shell; no next step for a visitor. | Added sign-up/sign-in actions, responsive auth forms, status/error feedback, and a profile page with sign-out. |
| Medium | GitHub CI is configured but has not run on GitHub. | Local checks do not prove remote service containers or branch protection. | Keep as an open validation item after push; first workflow run must be inspected. |
| High | Collaboration product remains incomplete. | Phases 3–10 cover workspaces, projects, boards, tasks, board events, presence, comments, and activity; the notification inbox, attachments, and search remain. | Continue by roadmap phase. Do not claim MVP or production readiness. |
| High | An invited user's post-login destination could be lost or redirected unsafely. | OAuth callback originally always sent users to `/app`; accepting a raw `next` URL could create an open redirect. | Restrict continuation to `/invite/<token>` and carry it through OAuth in a short-lived HttpOnly cookie. Added a redirect safety unit test. |
| Medium | Next.js development and production builds wrote the same `.next` directory concurrently. | A build failed with missing chunks while the local dev server was running. | Stopped the dev server and reran the build successfully. Do not run dev and build simultaneously in one checkout. |
| High | Nested project/board IDs could bypass workspace boundaries if trusted directly. | IDs can be guessed or copied from another workspace; checking only a supplied workspace ID would authorize the wrong tenant. | Phase 4 API resolves project → workspace and board → project → workspace before each read or write; integration tests cover outsider 404 and viewer 403. |
| Medium | Concurrent column edits could silently overwrite ordering. | Two administrators can load the same board version and submit conflicting order changes. | All column mutations claim the expected board version in a serializable transaction; stale requests return 409 and the web page explains the conflict. |
| Medium | A Next.js redirect thrown inside a `try` block was caught as a save failure. | The first column move action draft would turn a stale-version redirect into a generic error. | Moved validation redirects outside the request `try` blocks. |
| High | A task could be placed in a column from another board if only the column UUID were checked. | A cross-board pair would corrupt ordering and bypass the intended project boundary. | Phase 5 checks the target column and task lineage in the API and adds a composite `(column_id, board_id)` foreign key. |
| High | Removing a member left task assignment rows pointing to that former member. | Current members could continue seeing a former member as assigned. | Member removal and leave clear that user's assignments in the workspace in the same serializable transaction. |
| Medium | Concurrent unrelated invitation acceptances occasionally produced a retryable serializable conflict. | Parallel integration suites intermittently received 409 on a valid invite. | Retry PostgreSQL `P2034` up to three times; repeated integration runs pass. |
| Medium | Task drag/drop can fail after an immediate visual move. | Network, version, or permission errors could leave the board showing an incorrect position. | Client restores the previous list and shows an error; successful mutation refetches canonical state. |
| High | An open socket could receive board events from a workspace it no longer belongs to. | A valid login token alone does not authorize every board; membership can change after connection. | Phase 6 checks board lineage and workspace membership at `board.join`, disconnects sockets on member removal/workspace archive, and expires sockets with their JWT. Integration tests cover denial and revocation. |
| Medium | Parallel integration suites occasionally conflict in PostgreSQL serializable transactions. | A valid board column creation returned 409 while unrelated suites ran concurrently; the same test passed alone. | Run integration files serially in CI and locally; production mutations retain explicit 409 conflict behavior. |
| Medium | Live board changes required manual page refresh. | Phase 5 had local optimistic moves but no remote invalidation. | Phase 6 emits task/board events after successful REST writes; the board client deduplicates and refreshes on event/reconnect with a visible connection state. |
| Medium | A user could appear offline after closing one of several tabs. | Per-connection state without aggregation would report the first disconnected tab as an offline user. | Phase 7 uses atomic Redis leases per socket; online/offline changes on first join and last leave. Integration tests open two viewer sockets and verify no premature offline event. |
| Medium | Rapid repeated move input could send two versioned writes before the pending button state rendered. | The board checked React's `pending` state, which updates after the current event loop. | Phase 8 adds a synchronous pending guard; a two-writer API test verifies one 201, one 409, and canonical state from the winner. |
| High | Unchecked task-room joins would expose comments or typing across workspaces. | A task ID alone is insufficient permission, and archive/removal may revoke access after a connection opens. | Phase 9 resolves task → board → workspace before joining, evicts task/project/workspace sockets on archive, and tests outsider denial. |
| Medium | Mentions could notify a non-member or render unsafe markup. | Free-form comment text may contain arbitrary addresses or HTML. | Mentions resolve only current workspace member emails in a transaction; unknown addresses return 400. The web renders comment text as escaped React content. |
| Medium | A history write could fail after its primary mutation committed. | Reporting a 500 at that point could lead a user to retry a successful action and duplicate it. | Phase 10 logs the activity failure while preserving the successful mutation response. This leaves a possible history gap until a transactional outbox is added. |

## UI and accessibility review

The landing, sign-up, and unauthenticated redirect were inspected in a narrow browser viewport. The page hierarchy, keyboard focus styling, labels, disabled states, and status text are present. The form is readable on mobile; the card has appropriate spacing. Phase 3 adds workspace empty/error states, member labels, and confirmation for owner transfer/archive. Phase 4 adds project/board empty states and keyboard operable column ordering; the board supports horizontal scrolling at smaller widths. Phase 5 adds task cards, detail forms, conflict feedback, drag/drop, rollback, and keyboard arrow movement. Phase 6 adds visible live connection status and refresh on remote changes. Phase 7 adds a workspace online list that distinguishes a Redis presence outage. Desktop and authenticated screens have not been visually inspected in a live browser. Live sign-in, confirmation email, invitation acceptance, and Google OAuth cannot be exercised without a Supabase project and OAuth provider configuration.

## Verification

The Phase 2 API integration test covers missing/malformed/expired/wrong-audience tokens, a valid signed token, profile persistence, and invalid profile input with a local JWKS server and PostgreSQL. Phase 4 integration covers default board creation, authorization through resource lineage, stale board versions, ordering, and project archive. Phase 5 integration covers task RBAC, rank moves, cursor ordering, assignments, labels, deletion safeguards, copy, archive, and hard delete. Phase 6 integration covers socket authentication, room isolation, task/board event delivery, and membership revocation. Phase 7 extends it with multi-tab presence and heartbeat checks. Additional commands and outcomes are recorded in `process.md`.
